# Documentation screenshots

The screenshots on [rocketshow.net/docs](https://rocketshow.net/docs) are taken
by `capture.js` from the real web app, with demo data instead of a device
behind it. When a screen changes, retake them instead of editing images by
hand.

## Retake them

From the repository root, with the website checked out next to this
repository (`../spark`):

```shell
# 1. Build the web app (writes src/main/resources/static)
cd src/main/webapp && npm install --force && npm run prod && cd -

# 2. Install Playwright and its Chromium, once
cd docs/screenshots && npm install && npx playwright install chromium && cd -

# 3. Take all the shots
node docs/screenshots/capture.js
```

The images land in `../spark/website/assets/images/docs/` as `<name>.webp`,
ready to commit in the website repository. The pictures of the other pages of
the website (the phone on the home page, the composition editor and the
settings on the features page) land one folder up, in
`../spark/website/assets/images/`. Options:

| Option         | Meaning                                                        |
|----------------|----------------------------------------------------------------|
| `--only a,b`   | Retake only these shots, e.g. `--only settings-audio,designer` |
| `--list`       | Print the shot names                                           |
| `--app <dir>`  | Use a web app built somewhere else                             |
| `--out <dir>`  | Write the images somewhere else                                |

Nothing else is needed: no Raspberry Pi, no Java backend, no audio or DMX
hardware. The script serves the built app itself and answers every `/api`
request and WebSocket from the demo data.

A full run takes a few minutes. The full designer shot is the slow one: without
a graphics card, Chromium renders its 3D stage in software.

## The demo data

Everything the screenshots show comes from `demo-data/`. Edit it there, then
retake the shots:

| File                                    | What the device returns                                  |
|-----------------------------------------|----------------------------------------------------------|
| `settings.json`                         | `GET /api/system/settings`: audio buses, MIDI, lighting universes, triggers, scheduler, network, instruments, API keys |
| `system.json`                           | Everything else the app asks the device: login state, device information (SPARK and community edition), versions, play state, audio/MIDI devices, OLA plugins and ports, disk space |
| `compositions.json`                     | `GET /api/composition/list` and `GET /api/composition?name=` |
| `sets.json`                             | `GET /api/set/list`, `GET /api/set/details` and the loaded set |
| `media-files.json`                      | `GET /api/file/list`, the media library                  |
| `lead-sheets.json`, `lead-sheet.svg`    | The lead sheet library, and the image shown for each one |
| `designer/project-summer-tour-2026.json`| The lighting designer project: fixtures, presets, scenes, the timeline |
| `designer/fixtures.json`                | The fixture pool search list                             |
| `designer/profile-*.json`               | The fixture profiles (Open Fixture Library format) used by the project |

The Play screen lights the scenes of the designer project by hand
(`GET /api/scenes/projects` is made from it), so the project is written for
both: the scenes of “Neon Skyline” are in one folder and the looks between the
songs in another (the Play screen shows them as tabs), with icons and colours.
It also shows the features of the designer the docs explain: two tracks and
markers on the timeline of “Neon Skyline”, a hold point in “Intro – Countdown”,
the moving heads fanned out on the pan, a colour gradient fanned over the PARs,
and two LED pixel bars with a pixel effect. It is a project of the current
version, so the designer opens it without a warning; raise it when the
designer's project version goes up.

The audio behind the designer's timeline waveform is generated by the script,
so no audio file is stored here.

The demo show is a band, "Main Stage", on its "Summer Tour 2026": a set of
nine compositions with backing tracks, click, MIDI, video, lighting and lead
sheets. Keep it coherent when adding to it, since the documentation text
refers to it by name.

## Adding a shot

Shots are the `SHOTS` list at the bottom of `capture.js`. Each entry names the
image, the route to open, and optionally:

- `device`: how the fake device behaves for this shot, e.g.
  `{ edition: 'community' }`, `{ auth: { authenticated: false } }`,
  `{ state: { playState: 'STOPPED' } }`, `{ session: { playViewMode: 'grid' } }`,
  `{ session: { playMode: 'scenes' } }` (the scenes on the Play screen),
  `{ project: { selectedPresetUuid: … } }` (the designer project with something
  else selected) or `{ sceneMidi: [...] }` (MIDI keys learned for scenes)
- `run`: what to click before the picture is taken
- `element`: a selector to crop the picture to, e.g. a dialog
- `viewport`, `scale`, `mobile`, `fullPage`
- `localStorage`: what the browser keeps, e.g. `designerLayout` for how the
  designer shares the room between its panels (see `layout()` in the script)
- `file`: where the image goes instead of `<name>`, relative to the docs folder,
  e.g. `'../app-home'` for a picture of another page of the website

Keep a name once the docs page uses it: `website/docs.php` in the spark
repository refers to the images by name.

## The online designer

The pictures of the online designer (the large one on the designer page and
elsewhere, and the AI designing looks) need what only the online designer has:
the menu with Share and the user, and the AI. They are taken in the
show-designer repository from the same demo project, see
`web/screenshots/README.md` there.
